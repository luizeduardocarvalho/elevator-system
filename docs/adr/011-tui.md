# ADR-011: Terminal UI: renderer decoupling, fixed timestep, seek by re-simulation

## Status

Accepted (stage 3, branch `stage3-tui`, 2026-10-21). Builds on the shared v3 contract (steppable engine,
`IFaultInjector`, `DispatchEvaluated`), ADR-003 (sim clock, pure core) and ADR-007 (the event log is the backbone).

## Context

The spec's Hard level asks for a visual view of the building. The CLAUDE.md constraints are specific:
- Spectre.Console, about 20 fps, reading snapshots; the renderer **never drives the simulation**.
- Speed control with a **fixed sim tick plus an accumulator** (0.25× … 50×, MAX, pause, single-step), a **cap on
  ticks per frame**, and the **achieved speed shown**.
- **The same seed must give an identical event log at any speed.**
- `tui <scenario>` (live) and `replay <log.jsonl>`, backward seek, operator keys m / e / s calling `IFaultInjector`
  on the selected elevator (a no-op until the Hard stage, shown as "(no-op)").
- It is built in parallel with the Hard stage against a frozen contract, so it must render maintenance, emergency and
  fault modes and ops numbers that nothing emits yet, and must not crash on events it does not know.

## Decision

### Spectre.Console, and three layers so the renderer is dumb

1. **`BuildingState`, a fold over the event log.** Elevators (floor, state, shown direction, riders, mode,
   utilization), waiting ▲/▼ per floor, waits, ops counters and the event tail, built **only from events**.
   - Live, the TUI owns a `SimEngine` (`Create` + `AdvanceTo`, `EmitDispatchEvaluations = true`) and folds the
     engine's new log entries after each tick. In replay it folds the file.
   - **One folder for both**, so a replay shows what the live run showed by construction.
   - It is proved against the engine's own read-only views: at irregular sample times on five scenario × dispatch
     combinations, every elevator's floor, state, shown direction, riders and mode, the waiting counts and the
     delivered count equal `SimEngine.Elevators` / `Waiting` (`BuildingStateTests`).
   - The fold, not `SimEngine.Elevators`, is the render source because replay has no engine; reading snapshots live
     and events in replay would make the two views diverge.
   - *Shown direction* (identical from snapshots and events): moving → travel direction; doors open or closing → the
     lantern (`DoorsOpened`, or a hall call answered while open); otherwise none.
2. **`ScreenModel ViewModel.Build(BuildingState, ViewOptions)`, a pure view model.** Records of strings and enums
   (building grid, metrics, ops, event tail, status bar, help) with **no Spectre types**, unit-tested on its own
   (`ViewModelTests`): glyphs per state and door (▲ ▼ moving, ■ idle, ◧ □ ◨ doors, ✖ parked), D / M / E / F mode
   markers from synthetic v3 events, waiting counts, the ASSIGN line with every candidate's cost (∞ for ineligible)
   and the winner, a generic `key=value` line for unknown events, metric maths, "(no-op)", and graceful degradation
   (compact cells on narrow terminals, a floor window around the selected elevator on short ones, a "too small"
   notice below 40×12).
3. **`SpectreRenderer`: `ScreenModel → Layout`.** A mapping from tones and kinds to styles. With input polling it is
   the only Spectre-dependent code. It never sees the engine or the state.

**Unknown events never crash.** The log reader turns a line of an unknown type into an `UnknownEvent` (type plus
flat fields; a line that is not JSON becomes `UNREADABLE`). Any event without a dedicated tail format, known or not,
renders as `t  Type  key=value…` built from its JSON. The TUI adds **no event types**: `UnknownEvent` is a TUI-side
record, not a `DomainEvent`.

**Metrics.** Wait avg / p95 (nearest rank, ADR-008) / max over boarded passengers; % long waits (> 60 s); served,
active (waiting + riding); per-elevator utilization = share of sim time not idle (moving or in a door cycle; parked
does not count). **Ops:** maintenance time per elevator, emergency stops (count, time), faults (count, time until
recovered), reassignments (all, plus the ops ones: pickups handed back for maintenance, emergency or fault, with the
time those passengers then spent unassigned), commands applied and access denials. All zero until Stage 4 emits
events.

### Fixed sim tick, accumulator, cap, budget (`Pacer`, `TuiLoop`)

- **Tick:** 100 ms of sim time. The engine is only ever advanced in whole ticks. (The log is step-independent anyway,
  shared v3 contract; the fixed tick also keeps seeks on a grid.)
- **Accumulator:** each frame adds `realDelta × speed`, runs every whole tick it holds and carries the remainder. At
  20 fps, 0.5× is exactly one tick every fourth frame; 10× is five ticks per frame.
- **Cap and budget:** at most 2,000 ticks and about 30 ms of work per frame. **The excess is dropped, not carried**,
  so a slow frame (debugger, laptop sleep) cannot start an ever-growing catch-up; the achieved speed shows the
  shortfall. MAX = as many ticks as fit in the budget, up to the cap.
- **Achieved speed** = sim time advanced / real time over the last second of frames, next to the target.
- **Speeds:** 0.25×, 0.5×, 1×, 2×, 5×, 10× (default), 50×, MAX. Pause, single-step (one tick).
- **The loop takes an injected frame clock, key source and presenter.** Tests run thousands of frames instantly with
  a fake clock, no sleeping; `--plain` uses a virtual clock the same way for CI.
- **Keys:** space pause · n step · + / - speed · ← / → select elevator · m maintenance on/off · e emergency stop/clear
  · s stuck 60 s · [ / ] seek ∓60 s · 0 restart · q quit. m and e choose on/off from the folded mode. Ctrl+C cancels the
  loop; the alternate screen and the cursor are restored on every exit path.

### Seek: re-simulate live, re-fold in replay

- **Live backward seek re-simulates** (as asked): a fresh engine runs at full speed to the target, which is rounded
  down to the tick grid. The sim is deterministic, so the past is reproduced exactly. **Operator commands are the one
  input that is not in the scenario**, so the session records each one with the sim time it was injected at, and
  re-injects it at that time on the way. Commands after the target are dropped: going back and continuing starts a
  new timeline. Forward seek just runs ahead.
- **Replay seeks by re-folding the log from the start, not by re-simulating.** This is where I partly disagreed
  with the prompt, and the plan was approved with this deviation:
  - the log is the source of truth (ADR-007);
  - it may come from the non-deterministic actor runtime, or from an older build whose simulation differs;
  - it does not carry the scenario: `SimulationStarted` has the name and seed, not the YAML;
  - folding is cheap. A whole lunch log (6,912 events) re-folded to its last second: the `replay --plain --at 1838`
    process takes 0.24 s wall, startup included.

## Consequences

**Measured** (Debug build, Apple M2 Pro, 10 cores, macOS 26.5, .NET 10.0.301, load average ≈ 7):
- **Determinism at any speed.** `lunch` and `demo` driven by the real loop at 0.5× and 10× (fake 20 fps clock)
  produce the same log hash as a headless run with explanations on. With the `DispatchEvaluated` lines removed, they
  match plain `SimEngine.Run` byte for byte. Pausing, single-stepping and changing speed mid-run also leave the log
  unchanged (`LoopTests`).
- **Replay = live.** A loop-driven live run, written to JSONL and replayed, gives identical screens (building,
  metrics, ops, tail, clock) at every sampled time and frame by frame (`ReplayAndSeekTests`). One fix this test
  forced: the live session now delivers the messages due at t = 0 before its first frame, as a replay at 0:00:00.0
  shows them.
- **Seek-back = fresh run**, including re-applied operator commands. This is proved with a test injector whose
  commands post a passenger, so a command applied at the wrong time would change the log.
- **Speed in a real terminal** (130×40 pty, `lunch`): 0.5× and 50× achieve 0.5× and 50.0×. MAX hits the
  2,000-tick cap (200 sim s per frame) and achieves about 1,800×, finishing the 30-minute lunch in about a second of
  real time. A full headless `tui --plain --speed max` run of lunch (18,388 ticks) takes 0.27 s for the whole
  process.

**Trade-offs and limits:**
- **Two sources of truth for the screen (engine snapshots vs the fold) are avoided, at a cost:** the fold must keep
  up with event semantics. The folder-vs-engine test is the guard. When Stage 4 sets `Mode` on snapshots, that test
  starts checking modes against real data with no change.
- **Load is shown as riders/capacity.** `PassengerBoarded` carries no load units, so for freight (load > 1) the
  count is people, not units. Showing units would need a contract change (a `Load` field on the event); not
  requested.
- **The ops reassignment penalty** is measured directly: time from an ops hand-back to the next acceptance. It is
  not the ADR-008 `reassignment` + `blocked` buckets, because recomputing `PassengerLifecycle` over the whole log at
  20 fps is O(log) per frame. `run` and `bench` reports keep the exact buckets.
- **The injector is the engine's.** `tui` uses `SimEngine.FaultInjector` (no-op today). Stage 4 wires its injector
  through `SimEngineOptions.FaultInjector`, and `LiveSession` already accepts that factory. The status bar's
  "(no-op)" then disappears by itself.
- **Commands in a live run** reach the engine through `IFaultInjector` only. The log records them (Stage 4's
  `FaultCommandApplied`), so `replay` shows them with no extra mechanism.
- **The renderer is not unit-tested beyond "renders at any size and shows the key elements"**; all logic worth
  testing is in the view model.

## Amendment: fleets wider than the terminal (2026-10-22)

The TUI threw on fleets of 16 or more elevators. The Metrics and Ops panels listed every elevator, outgrew the rows
beside the building, and Spectre.Console's `Panel` rejected the negative height. Before that point the shafts were
squeezed until their headers and floor numbers became `…` (14 elevators at 120 columns).

A wide fleet is now handled the way a tall building already was, by a window around the selected elevator, which ←/→
move:
- **Shafts:** non-compact cells if they all fit, compact cells if those all fit, otherwise the compact shafts that fit,
  with `◀n` / `n▶` edge columns counting the elevators hidden on each side.
- **Side panels:** Metrics and Ops list the elevators that fit, and their headers show the range (`E0–E8 of 20`).
  They may take rows from the event tail, down to its minimum of 3 lines, so a short building no longer crops them.

The building-wide numbers (waits, served, totals) still cover the whole fleet. The view model decides all of this, so
it is unit-tested. A renderer test renders fleets of 1, 8, 16, 20 and 40 elevators at six terminal sizes, each with
three selections. Frames of the 4-elevator scenarios are unchanged byte for byte. `scenarios/tower.yaml` (40 floors,
20 elevators) exercises it.
