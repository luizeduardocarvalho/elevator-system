Architecture: pure core, threaded shell

All decisions live in pure, single-threaded handlers. Two shells deliver the same messages to them: a deterministic simulator for experiments and tests, and a real actor runtime for latency and concurrency. Everything that is measured is read from one event log.

The system and the lab

The projects split into the system, which is what would ship, and the lab, which is what we use to study it. Dependencies point one way: the lab depends on the system, never the reverse. An architecture test checks the declared project graph, the compiled references and the namespaces of every system project (ADR-019).

Elevator.Domain system

State machine with an explicit transition table; advances only through Tick(simTime). Handlers implement Handle(message, now, outbox).

Elevator.Policy system

LOOK scheduling, dispatch (Cost, with Nearest as the overload fallback) and access policies, as pure functions over immutable snapshots. Superseded strategies were removed once measured (ADR-018) and live at tag v3-full-grid.

Elevator.EventLog system

The JSONL wire format, one event per line. The event records themselves live in the domain, which emits them.

Elevator.Runtime system

One actor loop + Channel<T> mailbox per elevator, a single dispatcher on a bounded request channel, a log writer, a watchdog, the wall-driven RealClock and the runtime defaults.

Elevator.Metrics system

Reads the event log only: wait/ride/journey, wait attribution buckets, ops metrics, the wait heatmap, Student-t CIs.

Elevator.Simulation lab

SimEngine, SimClock, seeded Poisson traffic, YAML scenarios, fault injector. One seeded RNG → fully deterministic.

Elevator.Lab lab

Experiments against the real runtime: perf bursts, the soak, the open-loop throughput ramp, and the scenario → runtime options mapping.

Elevator.Tui lab

A fold over the log; reads at ~20 fps and never drives decisions. Same view for live runs and replays.

Dispatch: the cost function

cost(e, r) = ETA + λ·ΔD + μ·L̂/C, lowest wins (λ = 0.5, μ = 10 s, from a weight sweep on seeds 1–20, reported on held-out seeds 21–40).

  • ETA: seconds until elevator e would pick request r up.
  • ΔD: extra seconds everyone already riding or assigned would spend if e also takes r.
  • L̂/C: predicted load at pickup over capacity (the spec's balanceLoad()).
  • The terms come from a route projection: the elevator is replayed forward with its own scheduler and mechanics, with and without r. StopProjection (per stop, O(floors²), backlog-independent) is checked against the per-passenger RouteProjection oracle on 1,500 random elevators.
  • Eligibility comes before cost: an elevator an access policy denies is invisible to every dispatch path.

The simulation

A discrete-event simulator turns "is LOOK + Cost better?" into a paired experiment: same passengers, different strategies, confidence intervals.

The engine

  • SimEngine is one priority queue of messages keyed on (sim time, sequence number). Ties break by insertion order, so a run is a pure function of (scenario, seed, strategy).
  • It delivers the same protocol messages as the actor runtime, to the same handlers. There is no simulator-only logic.
  • Steppable: Create → AdvanceTo(t) → Finish. The TUI advances it in fixed 100 ms ticks; speed only changes how many ticks per frame.
  • Emergency stops get a priority key in the queue, so they preempt queued traffic at the same instant.

Two kinds of time

  • Sim seconds: wait, ride, journey, maintenance time, detection time. Deterministic.
  • Wall-clock ms: assignment latency in the actor runtime. Depends on the machine; only measured by perf.
  • They are never mixed in one metric.

Traffic

  • A non-homogeneous Poisson process with a piecewise-linear rate λ(t), generated by thinning (Lewis–Shedler): draw candidates at the peak rate λmax, keep each with probability λ(t)/λmax.
  • An origin/destination mix per profile: up-peak (mostly from the lobby), down-peak (mostly to it), lunch (both, two humps, 12/min peak, 6/min trough).
  • Scenarios are YAML: building, fleet types, access rules, traffic, latency, and a fault schedule.
name: lunch
seed: 1
building: { floors: 20, elevators: 4, capacity: 10, bypassThreshold: 0.8 }
scheduling: look

  profile:
    lobby: 1
    mix: { fromLobby: 0.40, toLobby: 0.40, interfloor: 0.20 }

      - { atS: 450,  perMinute: 12 }
      - { atS: 900,  perMinute: 6 }
      - { atS: 1350, perMinute: 12 }

How a result is measured

  1. Common random numbers: for a given seed every strategy sees exactly the same passengers.
  2. Paired differences per seed against a baseline, with a 95% Student-t interval; a Δ whose interval excludes 0 is marked ✱.
  3. Tuning vs held-out seeds: seeds 1–20 for exploring and weight sweeps, 21–40 for every reported decision.
  4. Wait attribution: each passenger's wait is split into buckets (dispatch, reassignment, bypassed_full, blocked, finishing door cycle, serving others, travel toward / away) that sum exactly to the wait. This explains why a strategy wins.
  5. Every results file records the exact command that produced it and regenerates byte-identically.

Rebalancing was measured and left off. On top of cost dispatch it saves at most 0.8 ± 0.5 s on average (down-peak), is not significant at up-peak or lunch, and moves about one passenger in eight to a different elevator. Under destination dispatch the passenger has already been told which door to go to, so each move sends someone to the wrong door: a real cost that the simulation does not model. That doesn't justify it, so assignments stay sticky. Rebalancing was then removed from main (ADR-018); it runs at tag v3-full-grid.

Thread safety: single writers, not locks

The spec asks for "appropriate locks/mutexes", atomic state changes and no races in request assignment. We get all three without a single domain lock: every piece of mutable state has exactly one owner, and owners only talk through messages (ADR-005).

Why it is thread safe

One owner per state

Each elevator, the dispatcher and the passengers are owned by exactly one loop reading a SingleReader channel. No other thread can touch that state.

Immutable snapshots

The dispatcher never reads an elevator's memory. It sees immutable snapshots that arrive as messages.

No domain locks

The shell uses only channels, a ConcurrentDictionary to correlate acks with callers, and a ConcurrentQueue log copy for tests. None holds domain state.

No lock across await

Since there are no locks, none can be held across a sleep or an await, and there is no lock ordering to get wrong.

Atomic state changes

  • Run-to-completion. A handler processes one message fully before the next is read. Every state change caused by a message, together with its events, is therefore atomic with respect to every other message for that elevator.
  • Explicit transition table. TransitionTable maps (state, trigger) → state; anything else is an illegal transition and throws. The tests check every edge.
  • Structural safety invariant. Moving states are entered only from Idle, which is reached only after DoorsFullyClosed, so "never moves unless doors are closed" is guaranteed by the table, not by a check.
  • Modes, not states. Maintenance, emergency and fault are an ElevatorMode derived from flags owned by the elevator. The emergency edges EmergencyHalt and EmergencyClose go through the same table.

Race conditions and how each is handled

RaceHandling
Two callers' requests land on the same elevator at the same instantRequests are serialised through the single dispatcher; elevators accept them one message at a time.
The dispatcher decides on a stale snapshotThe elevator has the final say: it accepts, or rejects (maintenance › capacity › stale > 10 s off its own projection). A rejected request is re-dispatched oldest-first. Aging (≥ 60 s) and forced proposals guarantee progress. The cost is visible in the reassignment wait bucket.
A burst of proposals before any snapshot returnsA pending-assignment overlay: the dispatcher adds its own in-flight proposals to each snapshot. Stale rejections at 100 simultaneous submitters dropped from 3.6 proposals per request to ≈ 1 per request and 0 rejections.
A request logged before its passenger existsCausality by construction: the caller waits for room in the bounded queue, then the passengers actor logs the arrival and submits the request in one handler call. (Found by the ordering audit: with a busy passengers actor, 277 of 800 requests were logged out of order; now 0.)
A request owned by two elevatorsOwnership changes only through accept / release messages handled by the dispatcher; asserted in every stress and property test.
An elevator handed pickups back while it still looked in serviceOn every path the elevator publishes its new snapshot first, and the release travels with the same link delay, so the dispatcher never proposes a pickup straight back. Hand-backs go out oldest call first.
Two delayed messages from one sender cross in the runtimeOne ordered delay loop per system, keyed (due time, sequence): equal delays keep their order. The dispatcher also ignores a snapshot older than the one it holds.
An emergency stuck behind a queue of trafficA priority lane per actor (and a priority key in the sim queue) for emergency stop and clear, FIFO between them: an emergency behind 50 queued commands takes effect first, and a clear posted before a stop stays before it.
New requests vs control traffic at the dispatcherThe second and last priority rule: snapshots, acks and releases are handled before new submissions, so decisions use an up-to-date view. FIFO within each lane; pinned by a test (ADR-015).
Log ordering across actorsOne log-writer task assigns sequence numbers; consumers never depend on cross-actor order.
The rule behind all of these (ADR-015): FIFO where order is a correctness property, priority where urgency differs, fairness decided by the cost function, not queue position. An audit of every queue and ordered iteration found eight places that broke it; each was fixed with a test written first, and 19 deliberate ordering mutations are all caught by the suite.

How the response time is measured

  • Definition: wall clock from AssignRequest to the elevator's accepted assignment, queueing included. It is not the moment the dispatcher picks a candidate.
  • Recording: HdrHistogram per run; p50 / p99 / max reported.
  • Method: a burst of N callers released together, a fresh process per point, warm-up first, median p99 of 3 repeats, taken when the 1-minute load average was under 3.
  • Gate: PerfGateTests (1,000 submitters plus a soak) runs in its own non-parallel test collection; it passed 3 / 3.

Where the ≈ 4.5k number comes from

  1. The dispatcher is the one serial stage. Per request it spends 16.6 µs (13.8 handler + 2.8 delivery) on protocol work: ingesting the snapshot from each accepted assignment, the pending set and overlay, events, and channel writes. The Nearest decision itself is ≈ 1.4 µs.
  2. 1 / 16.6 µs ≈ 60k requests/s; measured 55–59k from 3k up.
  3. A burst of N waits about N / 57k s for its last request, so 100 ms ↔ ≈ 5.7k. Fixed overheads bring the measured crossing to between 5k (77 ms) and 6.5k (102 ms) for Nearest, ≈ 6.4k.
  4. The default spends cost-function time on the first 200 in flight, so on the curve it crosses at ≈ 4.5k. 10k needs ≈ 175 ms at that rate, hence the stretch FAIL (182 ms on the curve, 202 ms in the perf run).
  5. For scale, 10k simultaneous presses is more than the population of a 20-floor office building (≈ 1,500–2,000 people).

If more were needed (not done)

  • Shard the dispatcher per elevator bank, not per zone. Zoning one bank breaks the group optimisation the cost function exists for.
  • Batch assignment: drain the channel in batches and solve each as an assignment problem (Hungarian). One snapshot ingestion per batch, and possibly better quality than greedy.

Errors, failures and faults

Every failure mode is either rejected at the boundary with a reason, or turned into a message that the single owner handles. Nothing is silently dropped, and every outcome appears in the event log.

Operational faults (ADR-013)

SituationWhat happens
Maintenance requestedMode becomes Draining; every pending pickup is handed back at once and reassigned; riders are still delivered. It then parks (Idle → Maintenance) and comes back on MaintenanceOff.
Emergency stopPreempts through the priority channel. If moving, it stops level with the next floor, doors closed (EmergencyHalt); if the doors are open, they close (EmergencyClose). Pickups are handed back; it takes no assignments until cleared.
Stuck elevatorThe watchdog, which rides on the dispatcher's snapshot stream plus per-floor progress reports, declares a FaultDetected after T = 30 s without progress. Its pickups are reassigned; FaultRecovered when it moves again.
Capacity fullNext-trip mode: a full elevator bypasses pickups and keeps them for its next trip; the elevator rejects if a request wouldn't fit. Riders left behind are counted and re-served.
OverloadAbove 200 requests in flight, dispatch falls back to Nearest, so latency stays bounded instead of collapsing.
Queue fullThe bounded request channel makes submitters wait asynchronously (backpressure); nothing is dropped.
Actor crashA faulted loop surfaces as ElevatorSystem.Fault; perf and the soak fail loudly with the inner exception instead of reporting numbers.

Bugs the tests caught

  • Eligibility deadlock: an early cost rule made every elevator permanently ineligible at capacity 1 with threshold 0.5. Found by a random-building property before any bench ran.
  • Projection staleness: a stale projection made LOOK + Cost worse than LOOK + Nearest (37.5 vs 19.2 s) with 480 stale rejections; after the fix, 0 rejections at zero latency.
  • Race detector check: deliberately adding a second writer makes the stress test fail at once.
  • Over-strict invariant (merge step): FsCheck found a rebalance handing a passenger over as the doors opened, so they boarded second in the same batch. Not a skip; the invariant now treats a door opening as one batch, and the seed is pinned as a regression.
